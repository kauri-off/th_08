## 1. Files and container format

### 1.1 `thbgm.dat` — the PCM container

- Size 449,961,024 bytes (0x1AD1DC40). [V]
- 16-byte header (read once at sound init, `FUN_004477b1`): [V]

| off | size | value required by engine | meaning |
|---|---|---|---|
| 0x00 | u32 | `0x5641575A` = ASCII `"ZWAV"` | magic |
| 0x04 | u32 | `1` | version? (checked, exact meaning unknown [I]) |
| 0x08 | u32 | `0x00000800` (2048) | some granularity/size value (checked; semantics unknown [I]) |
| 0x0C | u32 | not checked, shipped as 0 | unused |

- If the file cannot be opened the header check is skipped (no fallback error path observed). [V]
- The engine treats the file as one blob: every track's byte offset in the fmt table is an absolute
  file offset (track 0 starts at 0x10, right after the header). [V: first fmt record `start` == 0x10
  and playback seeks are `start`-relative from file position 0]
- Two container names exist in the binary: `"thbgm.dat"` (string @0x004B67CC) and `"th08.dat"`
  (@0x004B66C4). The name is selected by the global `DAT_018BDC7C` (“ZWAV base offset”), which is 0
  in this build and has **no writer anywhere** [V: single data xref chain, static 0]. So the
  `th08.dat` variant is dead code here [I].
- Track data is raw little-endian PCM. There are no per-track headers or RIFF chunks in the blob. [V]

### 1.2 `thbgm.fmt` — the track table

- Size 1109 bytes = 21 records × 52 (0x34) + 17 zero trailer bytes. [V]
- There is **no header and no record count**. The list is implicitly terminated by a record whose
  `name[0] == 0`; the zero trailer guarantees one exists (the name-scan loop was verified to walk
  `fmt + i*0x34` until a zero first byte). [V]

### 1.3 Record layout (per track)

| off | size | type | field | notes |
|---|---|---|---|---|
| +0x00 | 16 | char[16] | `name` | ASCII NUL-padded, e.g. `th08_00.wav` |
| +0x10 | 4 | u32 | `start` | absolute byte offset into `thbgm.dat` |
| +0x14 | 4 | u32 | `preload_bytes` | bytes copied in RAM-preload mode; always ≥ `length` in this file |
| +0x18 | 4 | u32 | `loop_start` | loop point offset relative to `start`; 0 ⇒ no loop point |
| +0x1C | 4 | u32 | `length` | total track length in bytes (= loop end) |
| +0x20 | 18 | WAVEFORMATEX | format | see §4 |
| +0x32 | 2 | u16 | (zero) | padding |

Record stride 0x34; every field alignment is 4. [V: consumer code indexes `rec = fmt + idx*0x34`]

## 2. Playback model (summary)

The engine is a DirectShow-SDK-derived streaming player. Names of duplicated Microsoft sample code
are visible in strings (`"HandleWaveStreamNotification"`, `"FillBufferWithSound"`,
`"Stream Skip"` …), so the streaming core is derived from the DirectShow WaveStream sample and
adapted. [V strings; I provenance]

Two operating modes exist:

1. **File streaming (default in this install).** One stream object is created over the whole
   `thbgm.dat`; track selection seeks within the already-open file. Gated by config option flag
   bit 13 (`DAT_017CE8A8 & 0x2000`); in this install the flag is 0 ⇒ file mode. [V]
2. **RAM preload.** With bit 13 set, `Bgm_PreloadTrack` mallocs `preload_bytes` and reads that many
   bytes from `start`, stores the buffer + record pointer per slot, and the DirectShow graph for the
   track is rebuilt in memory mode. [V]

Both modes are mixed at playback time: both play `[0, length)` once and then loop `[loop_start, length)`
(§3). Volume/pause/stop/fade are queued command types (see §6 table).

## 3. Intro / loop semantics (the key question)

**Result (byte-exact model):**

- A track's data region is `B` = `thbgm.dat[start .. start+length)`.
- Byte offset `loop_start` splits it: `intro = [0, loop_start)`, `loop body = [loop_start, length)`.
- Playback starts at byte 0 of the region, plays the whole region once, then loops the loop body
  forever. Loop end is `length` — **there is no separate loop-end field**.
- Loop point and all units are **bytes** (frame = 4 bytes, so `loop_start` is sample-exact and
  frame-aligned in practice).

### 3.1 Code evidence (all VERIFIED)

- `FUN_004733E0(obj, loopFlag)` is the DirectShow sample's `ResetFile` ported with a loop
  parameter:
  - `loopFlag == 0` **or** `loop_start < 1`: seek to `DAT_018BDC7C + start`; set remaining counter
    `obj+8 = length`.
  - `loopFlag == 1` **and** `loop_start ≥ 1`: seek to `DAT_018BDC7C + start + loop_start`; set
    `obj+8 = length - loop_start`.
  - Memory mode (flag at `obj+0x7C`): cursor = buffer base (plus `loop_start` when the flag is set),
    size = `length`. Same arithmetic on the RAM copy.
- The **only** call site that passes `loopFlag = 1` is at `0x00472FB0` inside `FUN_00472D30`
  (`HandleWaveStreamNotification`), reached when the stream reports it needs a refill after the
  queued data runs out (`local_10 < local_28`). That is the "wrap to loop point" event.
- `FUN_00473300(obj, rec)` (SetCurrentRecord) stores the record pointer at `obj+0x90` and calls
  `ResetFile(0)` — i.e. every track start includes the intro. [V]
- No use of `IMediaSeeking`/`SetStopTime` or any other loop primitive was found; the loop is
  implemented purely by this seek+remaining bookkeeping. [V]

### 3.2 Consequences

- Audible result: `intro` once, then `loop body` repeated indefinitely → a reimplementation must
  treat each track as (intro, loop, loop, …) with `loopEnd = length`.
- The first repetition of the loop body is exactly the tail of the first pass — the model does not
  decode a separate "second play" of the loop; `B` is simply re-entered at `loop_start`.
- Loop durations: `loop_s` column in §1.4; loop-body byte size = `length - loop_start` (4-byte aligned).
- Tracks whose `loop_start` were 0 would play the whole track as the loop body
  (`ResetFile(0)` path). No shipped track uses that. [V]

### 3.3 Streaming geometry (file mode)

- Graph built by `FUN_004718D0`/`FUN_00473250` over the whole blob; ring of **16 buffers × 44100
  bytes = 705,600 bytes = 4.0 s** with a DirectSound position-notify event per buffer; write
  position wraps `(pos+len) % obj+8` where `obj+8` is the current region remainder. [V]
- A refill that would overrun the region boundary reads `length - loop_start` from the loop point
  instead (under-run handling). This is what makes the loop sample-exact: the very same PCM bytes
  are re-emitted from `loop_start`, no gap and no crossfade. [V mechanism; I "sample-exact" phrasing]
- Silence padding uses `rec+0x2E` = `wBitsPerSample`: 0x80 for 8-bit, 0 for 16-bit PCM. [V]

### 3.4 `preload_bytes` (RAM-preload mode detail)

- `Bgm_PreloadTrack(slot, name)` (via `FUN_0045CE70`): dedupe against the slot's stored name,
  `CreateFileA` the container, `SetFilePointer(start)`, `malloc(preload_bytes)`, `ReadFile(...,
  preload_bytes)`, stores record ptr / buffer / size per slot. [V]
- `preload_bytes` is always larger than `length`; playback in memory mode is clamped to `length`,
  so the surplus is read but never played. [V data + clamp; I rationale: slack for the sample's
  buffer management]
- The preload path is skipped entirely when option bit 13 is clear (returns 0 without opening the
  file) — i.e. in the default configuration only the streaming path runs. [V]

## 4. Wave format and extraction recipe

### 4.1 WAVEFORMATEX in every fmt record

`(wFormatTag, nChannels, nSamplesPerSec, nAvgBytesPerSec, nBlockAlign, wBitsPerSample, cbSize) =
(1, 2, 44100, 176400, 4, 16, 0)` [V]

- PCM, stereo, 44100 Hz, 16-bit signed little-endian; frame = 4 bytes; 176400 bytes/s.
- The engine also has an `8-bit` silence-fill constant, but no shipped fmt record uses 8-bit. [V/I]

### 4.2 Extracting one track as a plain RIFF/WAVE file

For track `i` with PCM byte count `N` (`N = length`, or `N = length - loop_start` if you only want
the loop body, etc.):

```
"RIFF" u32(36 + N) "WAVE"
"fmt " u32(16) u16 1 u16 2 u32 44100 u32 176400 u16 4 u16 16
"data" u32(N)
<N bytes from thbgm.dat at offset start>
```

[V: this is the standard canonical WAVE header for the advertised WAVEFORMATEX; byte count formula
`36+N` is the standard RIFF size]

- Plain RIFF/WAVE cannot express the intro/loop split. If loop metadata must travel with the file,
  the standard way is a `smpl` chunk (`start`/`end`/`numloops=1`, sample units = bytes/4); the game
  itself does not use any such chunk. [I: recommendation, not game behavior]
- Loop values in samples (for `smpl` or playback loops): `loopStartSample = loop_start/4`,
  `loopEndSample = length/4`. [V derived]

fallback]

Consistent hypothesis [I]: the `_s` set belongs to the mode whose BGM is selected by the baked table
(bit 14 set), and its `+0x290` fields are not used at runtime in that mode. Needs a runtime check or
a trace of the `_s`-mode loader to settle (see §7).

## 7. Open questions / next checks (Phase 2 candidates)

1. **`DAT_0164D0B8` identity.** A monotonic-ish id read by the stage-start code, validated against
   per-stage windows (stage 6a: 119..122; 6b: 147..150; extra: 191..193 ± 213) and used as the key
   for table (b). Strongly looks like the spell-card id (spell practice); not traced to its writer
   definitively. [I]
2. **Mode that sets flag bit 14** (owner of the baked-table BGM path): routine `FUN_0046BBC0` sets
   `flags |= 0x4001` while building a 15-per-row spell-card grid; label/menu not traced to screen. [I]
3. **`_s` stage files** (§5.6): which mode loads them; whether their `+0x290` names are dead fields;
   `th08_02` / `th08_13_b` discrepancy. Runtime trace or loader trace needed.
4. **fmt record slack**: `preload_bytes` > `length` is read but unused; why the padding exists is
   not explained by the code seen. [I]
5. **ZWAV dword1/dword2 semantics** (1 and 0x800) — only checked, never used further. [I]
6. **Retail-order question**: the decoded archive fmt is lexicographic; the exe's compiled tables and
   musiccmt use music-room order. Whether *retail v1.00d* really shipped this way (i.e. index-based
   paths were already mismatched, or those paths were always shadowed) is unresolved. Runtime
   verification (breakpoint on `FUN_00447E47` in the relevant menu) would settle it.
7. **Volumes**: cfg `+0x27`/`+0x28` → volume queue mapping/tables not traced. [I]
8. SE subsystem (separate `.dat`) intentionally out of scope of this document.
